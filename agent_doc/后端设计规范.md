# 后端设计规范

## 目的与适用范围

本规范适用于 `pansis_toolbox` 中所有新建或重构的工具后端。它定义工具接入、路由、认证、数据、后台任务、异常与测试的约定。核心原则是：复用框架能力，不绕过平台权限边界；工具的持久化数据必须可定位、可按用户隔离、可独立统计和清理；工具代码目录不得成为运行时数据目录。

本文中的“持久化数据”包括数据库、上传文件、缓存、会话、日志、生成文件、运行时下载的依赖，以及浏览器端会跨刷新保留的数据。

配套文档：[前端设计规范](./前端设计规范.md) · [环境配置指导](./环境配置指导.md)。文中的“必须/不得”是验收要求，“推荐/宜”允许在设计摘要中说明理由后调整。

## AI 实现协议

使用 AI 创建新工具时，按以下顺序工作，不得直接从页面代码开始：

1. 阅读本文件、`前端设计规范.md`、`环境配置指导.md`，再查看一个与目标形态最接近的现有工具。
2. 先输出一页设计摘要：工具 ID、用户角色、核心资源、API、存储归属、外部依赖、后台任务、页面结构和风险边界。
3. 明确每类数据属于平台、工具公共数据还是用户私有数据；无法判断时默认按用户私有数据处理。
4. 使用 `python scripts/create_tool.py <tool_id>` 创建骨架，在骨架上实现，不手工绕过注册机制。
5. 先完成后端模型、授权与测试，再连接前端；所有资源查询先证明所有权，再返回数据。
6. 完成后执行本文末尾的验收矩阵。命令成功只是必要条件，还必须进行双用户隔离和页面流程检查。

AI 在开始编码前至少应给出下面这份摘要：

```text
工具 ID：
工具目标与非目标：
使用者：匿名 / 登录用户 / 管理员
核心资源及所有者：
公共数据：
用户数据：
框架服务：SSH / Email / GitHub Key / Proxy / Scheduler / Widget / 无
API 清单：
后台任务与超时：
前端页面、主弹窗与二级弹窗：
安全与失败场景：
```

## 工具接入契约

一个工具对应一个 `tools/<tool_id>/` 目录，至少包含：

```text
tools/<tool_id>/
├── manifest.json
├── backend/
│   ├── router.py             # 必须导出 router: APIRouter
│   ├── service.py            # 推荐：业务与数据访问层
│   └── scheduler.py          # 可选：导出 register_tasks(scheduler)
├── frontend/
│   └── index.tsx             # 默认导出 React 组件
└── tests/
```

`manifest.json` 是工具唯一注册入口。必须提供唯一的 `id`、`name`、`description`、`version`、`entry.frontend`、`entry.backend` 与 `api.prefix`；`api.prefix` 推荐使用 `/api/tools/<tool-id>`。`id` 使用小写字母、数字和下划线；URL 前缀可使用连字符。工具间的 ID 与 API 前缀均不得重复。

推荐从以下 manifest 开始，仅保留实际需要的权限和依赖：

```json
{
  "id": "example_tool",
  "name": "示例工具",
  "description": "一句话说明用户能完成什么。",
  "version": "0.1.0",
  "enabled": true,
  "category": "other",
  "icon": {"type": "lucide", "name": "wrench"},
  "displayMode": "standard",
  "entry": {
    "frontend": "frontend/index.tsx",
    "backend": "backend/router.py"
  },
  "api": {"prefix": "/api/tools/example-tool"},
  "widgets": [],
  "dependencies": {},
  "permissions": {
    "filesystem": false,
    "network": false,
    "longRunningTask": false,
    "userData": true
  },
  "dependsOn": []
}
```

`permissions` 当前是清单和管理界面的声明信息，不是操作系统沙箱，也不会自动阻止文件、网络或长任务；代码仍必须遵守本规范。`dependsOn` 只用于工具加载可用性判断，不会注入 Python 模块或共享数据。Python 包依赖写入 `dependencies`，工具自己的 Node 构建依赖写入该工具的 `package.json` 和锁文件。

框架会发现启用的 manifest，动态加载 `router.py` 中名为 `router` 的 `APIRouter`，并自动：

- 以 manifest 的 `api.prefix` 挂载路由；
- 在通过 `router` 注册的全部路由前执行工具访问控制；
- 将 `assets/` 挂载到 `/tool-assets/<tool_id>/`；
- 加载可选的 `mount_extra(app)` 和 `backend/scheduler.py`；
- 重建工具与小组件注册表。

工具不得自行在 `main.py` 注册，也不应修改框架路由、CORS、全局异常处理或认证中间件。新增、删除或修改 manifest 后运行 `npm run check:tools` 与 `npm run generate:tools`。

注意：`mount_extra(app)` 直接向应用注册路由，不继承 manifest router 的工具访问依赖。每个这类端点都必须显式调用 `require_tool_access(TOOL_ID, get_optional_user(request))`，再按需要调用 `require_user` 或资源授权函数。普通 JSON API 优先使用标准 `router`。

## 已有后端接口与服务

| 能力 | 可用接口 | 使用约定 |
| --- | --- | --- |
| 平台配置 | `backend.app.core.config.get_settings()` | 读取工具目录、存储根、平台数据库、前端来源等；不要在工具中重复读取 `.env` |
| 当前用户 | `require_user(request)` | 需要登录的端点首行调用，返回 `User` |
| 可选用户 | `get_optional_user(request)` | 公开端点可据此调整可见内容，不可据此前端数据授权 |
| 管理员 | `require_admin(request)` | 仅管理功能使用 |
| 用户目录 | `auth_service.list_users()` | 后端确需用户基础信息时使用；不得借此绕过资源授权或暴露密码字段 |
| 用户数据库 | `user_tool_connection_context(user.id, TOOL_ID)` | 事务成功自动提交、结束自动关闭 |
| 用户数据库路径 | `get_user_tool_db_path(user.id, TOOL_ID)` | 仅在确实需要文件路径的维护/统计场景使用，普通 SQL 使用连接 context |
| 用户文件目录 | `require_user_tool_data_dir(request, TOOL_ID)` | 返回当前用户工具目录并自动创建 |
| 全局平台数据库 | `connection_context()` / `get_connection()` | 只限平台框架状态，工具新业务不得使用 |
| 用户库遍历 | `list_user_tool_dbs(TOOL_ID)` | 仅后台任务批量处理时使用 |
| 业务错误 | `ToolboxError(code, message, status_code, tool_id, extra)` | 由框架统一序列化为 `{"error": ...}` |
| 数据分类 | `DataCategory`、`register_tool_categories()` | 声明可统计、可按类别/时间清理的数据表；管理接口负责统计和删除 |
| 数据维护 | `count_data()`、`get_data_usage_by_category()`、`delete_data()`、`prune_tool_data()` | 通常由平台设置页或工具 Scheduler 使用，不在普通请求中跨用户调用 |
| 定时任务 | `scheduler.add_interval_task(...)` | 在 `register_tasks(scheduler)` 中注册 |
| 工具访问控制 | `can_access_tool()`、`require_tool_access()`；标准 router 自动添加 dependency | 端点中仍须做资源所有权检查；`mount_extra` 显式调用 |
| 小组件 | manifest `widgets` 与可选 `get_widget_data(widget_id)` | 小组件应遵循工具访问权限 |
| SSH 连接池 | `SSHConnectionSpec`、`borrowed_client()`、`exec_command()`、`invalidate()` | 复用连接池；命令必须安全构造、设置超时，传输错误时使连接失效 |
| SSH 服务器 | `list_servers()`、`get_server()`、`get_server_credentials()`、`copy_server()`、`test_connection()` | 复用用户自有或被授权的全局服务器；凭据只在后端内部取得 |
| 邮件发送 | `email_service.send_email(recipients, subject, body)` | 使用管理员配置的统一 SMTP；工具只提供收件人、主题和正文，不管理 SMTP 密码 |
| GitHub Deploy Key | `github_key_service.list_keys()`、`create_key()`、`get_private_key()`、`delete_key()` | Key 由用户拥有；传入当前 `User`，私钥仅供后端 Git/SSH 调用，绝不返回前端 |
| 出站代理 | `proxy_service.get_proxy_url_for_host(host)` | 只对管理员已启用的域名返回全局代理 URL；工具不得自建或绕过域名路由策略 |
| 静态资源 | 工具根目录 `assets/` → `/tool-assets/<tool_id>/` | 只放随代码发布的只读资源；用户上传和运行时生成文件不能放这里 |

接口的签名与行为以 `backend/app/` 源码为准；新增通用能力应先在框架服务层实现，再供各工具复用。

### 当前框架限制

这些限制必须被 AI 视为事实，不能通过猜测接口绕过：

| 限制 | 新工具的处理方式 |
| --- | --- |
| `permissions` 不执行运行时沙箱 | 仍做最小权限设计，并在代码审查中检查真实 I/O |
| `mount_extra` 不自动附加工具访问依赖 | 每个根级端点显式校验工具访问和用户/资源权限 |
| Widget provider 只接收 `widget_id`，没有用户上下文 | 只返回公共、非敏感、快速数据；用户专属 Widget 需先扩展框架 |
| Widget layout 当前是平台单文件而非逐用户 | 新工具不要把用户业务状态塞入 Widget layout |
| 登录 Cookie 的 `Secure` 当前在代码中固定为关闭 | HTTPS 上线前需先修复平台认证实现，工具不得另建认证 Cookie 补救 |
| `check:tools` 只检查基础 manifest/入口与重复项 | 仍需执行测试、构建、存储扫描与人工验收 |

## 路由与 API 设计

1. `router.py` 只负责 HTTP 参数、Pydantic 请求/响应模型、认证入口和调用 service；复杂业务、SQL 和外部 I/O 放入 `service.py`。
2. API 采用资源导向路径和标准 HTTP 方法：读取 `GET`、创建 `POST`、整体更新 `PUT`、删除 `DELETE`。动作型端点只用于确实不等同 CRUD 的操作，例如 `/sync`、`/test`、`/start`。
3. 请求与响应必须使用 Pydantic 模型或清晰的类型标注；不得将数据库行、密码密文、内部路径、堆栈或第三方原始错误直接返回。
4. 每个读取、更新、删除单个资源的 service 查询都必须以当前用户 ID 或已验证的共享授权为条件。仅靠前端隐藏按钮不构成授权。
5. 文件上传应限制文件类型、大小、编码和文件名；下载应验证资源归属并使用安全的响应头。
6. `mount_extra(app)` 仅用于确实需要根级公开页面、代理或挂载点的工具。新增的根级路由必须使用唯一且文档化的前缀，不能覆盖平台路由。
7. 列表接口默认考虑分页、过滤和稳定排序；返回集合应使用一致包裹形式或明确的顶层数组，不在同一工具内混用命名风格。
8. 所有时间在后端以带时区的 UTC ISO-8601 字符串保存，API 字段使用 camelCase，与现有前端 DTO 保持一致。
9. Pydantic 的列表、字典等可变默认值使用 `Field(default_factory=list)` / `Field(default_factory=dict)`；输入字符串声明长度和格式边界，数字声明合法范围。
10. SQL 值一律参数化；表名、列名等 SQL 标识符不能来自未经白名单校验的请求参数。

推荐的错误写法：

```python
raise ToolboxError(
    "RESOURCE_NOT_FOUND",
    "资源不存在或无权访问",
    status_code=404,
    tool_id=TOOL_ID,
)
```

错误码使用全大写下划线名称，稳定且可供前端判断；可预期的输入、权限、外部服务错误均转换为 `ToolboxError`，未预期异常交由框架统一返回 500。

## 认证、权限与外部访问

- 工具路由已由框架进行“是否可访问该工具”的检查；这不替代资源级权限检查。
- 服务端始终从会话 Cookie 解析用户，不接收客户端指定的 `user_id`、`owner_user_id`、角色或权限作为可信依据。
- 管理员操作必须使用 `require_admin`；共享资源必须有显式拥有者、公开标志或授权表，并在每次访问时校验。
- 凭据使用框架提供的统一 SSH/GitHub 服务，或以当前用户工具数据中的密文保存。禁止记录明文密码、令牌、私钥、Cookie 或完整 Authorization 请求头。
- 需要邮件通知时复用 `email_service.send_email()`；发送前验证收件人和频率，并把 SMTP 配置、密码和连通性测试限制在平台设置的管理员接口。该服务目前会抛出普通异常，工具应转换为脱敏的 `ToolboxError` 或在后台任务中记录失败。
- 需要访问 GitHub 私有仓库时，使用 `github_key_service.get_private_key(key_id, user)` 获取当前用户自己的 Deploy Key；不得接受或返回私钥文本，也不得绕过所有者检查。应结合 `proxy_service.get_proxy_url_for_host()` 决定是否使用管理员授权的出站代理。
- 网络请求需设置超时、输入 URL 校验、响应大小限制和明确错误转换；命令执行必须避免 shell 拼接用户输入。

## 数据库、数据分类与生命周期

每个含数据库的工具应在 service 初始化时建立自己的 schema，并在模块加载时注册数据分类：

```python
register_tool_categories(TOOL_ID, [
    DataCategory("config", ["example_settings"], None, "用户配置"),
    DataCategory("history", ["example_runs"], "created_at", "运行历史"),
])
```

时间可清理的数据必须有 UTC ISO-8601 时间列；配置类数据的 `time_column` 为 `None`。表名应使用工具专属前缀，迁移必须幂等并兼容已有安装。删除、清理和后台任务不得在无明确范围时跨工具或跨用户操作。

## 后台任务与长任务

工具若有 `backend/scheduler.py`，必须导出：

```python
def register_tasks(scheduler):
    scheduler.add_interval_task(
        tool_id=TOOL_ID,
        name="refresh",
        interval_seconds=300,
        callback=refresh_all_users,
        run_immediately=False,
    )
```

定时回调应短小、可重复执行、捕获单个用户或资源失败，并通过 `list_user_tool_dbs(TOOL_ID)` 逐个用户处理。不要在导入模块时启动线程、事件循环或无限循环；框架负责任务启动、停止和异常隔离。长操作应提供状态、取消或超时策略，不能阻塞事件循环或 HTTP worker。

## 推荐后端骨架

`router.py` 只做协议适配：

```python
from fastapi import APIRouter, Request
from pydantic import BaseModel, Field

from backend.app.core.security import require_user
from tools.example_tool.backend import service

router = APIRouter()

class CreateItemPayload(BaseModel):
    name: str = Field(min_length=1, max_length=100)

@router.get("/items")
def list_items(request: Request) -> dict:
    user = require_user(request)
    return {"items": service.list_items(user.id)}

@router.post("/items", status_code=201)
def create_item(request: Request, payload: CreateItemPayload) -> dict:
    user = require_user(request)
    return {"item": service.create_item(user.id, payload.name)}
```

`service.py` 拥有 schema、SQL、所有权查询和序列化：

```python
from backend.app.db.database import user_tool_connection_context

TOOL_ID = "example_tool"

def _init(conn) -> None:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS example_items (
            id TEXT PRIMARY KEY,
            name TEXT NOT NULL,
            created_at TEXT NOT NULL,
            updated_at TEXT NOT NULL
        )
    """)

def list_items(user_id: str) -> list[dict]:
    with user_tool_connection_context(user_id, TOOL_ID) as conn:
        _init(conn)
        rows = conn.execute(
            "SELECT * FROM example_items ORDER BY created_at DESC, id DESC"
        ).fetchall()
    return [{"id": row["id"], "name": row["name"], "createdAt": row["created_at"]} for row in rows]
```

不要把示例中的简化返回类型当成免除响应契约；正式工具应为重要请求和响应声明 Pydantic 模型，并为 schema 初始化、迁移和资源授权写测试。

## 小组件与可观测性

在 manifest 中声明的小组件会以 `<tool_id>.<widget_id>` 注册。小组件后端可提供 `get_widget_data(widget_id)`；其返回值应小、快速、无敏感数据，并假定调用者已经通过工具访问控制。需要用户专属小组件数据时，现有接口没有传入请求或用户上下文，不应绕过此限制；先扩展框架接口。

使用标准日志记录运行状态、耗时和已脱敏的错误上下文。日志不应含用户秘密；持久化日志遵循本规范的数据目录规则。

## 强制目录模型

仅允许使用下面两个工具数据根目录：

```text
storage/
├── data/
│   ├── platform.db                    # 仅平台框架的账户、会话、全局设置
│   └── tools/
│       └── <tool_id>/                 # 该工具的公共内容与公共运行缓存
└── user_data/
    └── <user_id>/
        └── tools/
            └── <tool_id>/             # 该用户在该工具中的全部私有内容
```

规则如下：

1. `tool_id` 必须与 `tools/<tool_id>/manifest.json` 中的 ID 一致，只允许使用小写字母、数字和下划线。
2. 公共内容只能放在 `storage/data/tools/<tool_id>/`，例如管理员维护的公共模板、所有用户可复用的只读索引或不含用户信息的公共缓存。
3. 任何可以关联到某个用户的数据都必须放在 `storage/user_data/<user_id>/tools/<tool_id>/`，包括配置、凭据密文、历史、文件、会话、私有缓存、访问记录和用户创建的“可公开”内容。
4. 即使内容对外可见，只要由用户创建、拥有或可追溯到用户，也仍属于该用户目录；公开访问应由数据库字段和权限控制实现，而不是将内容移动到公共目录。
5. 工具不得在 `storage/<tool_id>/`、`storage/temp/`、`storage/uploads/`、`storage/outputs/`、`tools/<tool_id>/` 或其他任意目录持久化工具数据。
6. `platform.db` 不得新增工具业务表。平台账户、登录会话、平台级设置、工具可见性策略及由框架统一管理的 SSH 服务器、SMTP 配置、GitHub Deploy Key、出站代理配置除外。工具自身的表必须写入它所属的公共或用户专属工具目录中的数据库。

## 存储决策表

| 数据类型 | 正确位置 | 例子 |
| --- | --- | --- |
| 平台框架状态 | `storage/data/platform.db` | 用户账户、登录会话、平台 SMTP 配置 |
| 工具公共内容 | `storage/data/tools/<tool_id>/` | 管理员发布的公共模板、无用户标识的缓存 |
| 用户工具数据库 | `storage/user_data/<user_id>/tools/<tool_id>/data.db` | 用户配置、任务、历史、凭据密文 |
| 用户工具文件 | `storage/user_data/<user_id>/tools/<tool_id>/files/` | 上传附件、图标、导出结果、私有缓存 |
| 运行时临时文件 | 上述目标目录内的 `tmp/`，完成后删除 | 解压中间文件、渲染工作目录 |
| 前端偏好 | 优先服务端用户工具数据库 | 面板布局、筛选条件、最近选择 |

## 后端实现要求

### 用户专属数据库与文件

用户数据必须通过框架助手获得路径，不能自行拼接 `storage` 或调用裸 `sqlite3.connect`：

```python
from backend.app.core.security import require_user, require_user_tool_data_dir
from backend.app.db.database import user_tool_connection_context

TOOL_ID = "example_tool"

def save_preference(request, payload: dict) -> None:
    user = require_user(request)
    with user_tool_connection_context(user.id, TOOL_ID) as conn:
        conn.execute("INSERT INTO preferences (key, value) VALUES (?, ?)", ("theme", payload["theme"]))

def save_upload(request, filename: str, content: bytes) -> None:
    data_dir = require_user_tool_data_dir(request, TOOL_ID)
    target = data_dir / "files" / filename
    target.parent.mkdir(parents=True, exist_ok=True)
    target.write_bytes(content)
```

文件名必须去除路径成分、限制长度，并避免以用户输入直接构造目录名。需要跨用户后台扫描时，使用 `list_user_tool_dbs(TOOL_ID)`，不得改变数据库路径规则。

### 公共数据

公共文件路径必须集中定义，且只能返回该工具的目录：

```python
from pathlib import Path
from backend.app.core.config import get_settings

TOOL_ID = "example_tool"

def shared_tool_dir() -> Path:
    path = get_settings().storage_dir / "data" / "tools" / TOOL_ID
    path.mkdir(parents=True, exist_ok=True)
    return path
```

若公共数据需要数据库，使用 `shared_tool_dir() / "data.db"`；不要将表写入 `platform.db`。

### 临时文件、日志与运行时依赖

- 临时目录必须位于相应公共或用户目录的 `tmp/` 子目录，操作结束后清理。
- 工具日志应输出到进程标准输出，由部署平台收集；若必须持久化日志，按归属保存到工具目录。
- Node、Python 和其他运行时依赖必须在镜像构建阶段或开发环境安装，不能由请求处理代码在 `tools/` 下执行 `npm install`、`pip install` 或写入 `node_modules`。
- sidecar 的 session、cache、密码文件和运行日志也属于工具数据，必须显式传入上述合规目录。

## 前端与外部系统

- 不使用 `localStorage`、`sessionStorage`、IndexedDB 或 Cache Storage 保存认证信息、敏感数据或需跨设备同步的业务数据。低风险的匿名页面展示偏好可按 Cookie 规范保存。
- 需要跨设备同步、供后台任务读取、参与权限判断或可影响业务结果的状态必须回写后端；只影响当前浏览器展示的低风险状态可以使用 Cookie。
- 远程 SSH 主机、Docker 主机或第三方服务上的数据不受本地目录规则约束，但工具本地保存的连接配置、凭据、任务记录和缓存仍受本规范约束。

## Cookie 规范

Cookie 可用于浏览器与本平台之间的认证，以及低风险、按浏览器生效的页面体验状态。例如博客目录折叠状态、非敏感主题偏好或一次性提示已读状态。Cookie 不应用于敏感业务数据、跨设备同步数据或大体积缓存。

1. 平台登录使用统一的 `pansis_session` Cookie；工具不得自行创建第二套登录、用户 ID、角色或权限 Cookie。
2. 工具需要登录用户时，必须通过后端 `require_user` / `get_optional_user` 读取统一会话；不得信任前端传入的用户 ID、角色或 Cookie 内容。
3. Cookie 值禁止包含明文密码、访问令牌、SSH 凭据、个人隐私、完整业务对象，或任何可单独用于授权的内容。认证 Cookie 必须使用随机不透明会话标识或可验证签名值。
4. 认证 Cookie 必须设置 `HttpOnly`、合理的 `SameSite`、`Path=/` 和明确的过期策略；生产 HTTPS 环境必须设置 `Secure`。
5. 工具的展示偏好 Cookie 可以由前端读写，名称宜以 `pansis_<tool_id>_` 开头，并应使用尽可能小的 `Path`。既有公开博客目录状态 `git_blog_directory_collapsed` 以博客路径隔离，是允许的兼容场景。
6. Cookie 应保持小型；单个 Cookie 接近浏览器约 4 KB 限制时必须截断或改用后端存储。不得将上传内容、会话快照或大体积缓存序列化后写入 Cookie。
7. 代理或嵌入第三方网站时，第三方站点 Cookie 必须与该用户的工具数据隔离保存，不能写入平台域的认证 Cookie，也不能在用户之间复用。
8. 登出、用户禁用、会话失效和用户数据清理时，必须删除或使相关认证会话立即失效。纯展示偏好 Cookie 可自然过期或由用户清除。

## 清理、统计与迁移

1. 每个工具必须支持按用户删除 `storage/user_data/<user_id>/tools/<tool_id>/`，且不会影响其他用户。
2. 管理员清理工具公共数据时，只删除 `storage/data/tools/<tool_id>/`；不得误删平台数据库或其他工具目录。
3. 新增文件类型后，确认存储用量统计和清理接口能覆盖该路径。
4. 重构既有工具时，先迁移数据、验证数据完整性，再删除旧位置；不要把迁移逻辑放在每次请求的热路径。

## 测试规范

每个新工具至少覆盖：

1. manifest 能被发现，router 能加载，禁用或缺少依赖时状态正确。
2. 未登录、无工具访问权、普通用户、管理员四类访问结果。
3. 用户 A 创建的数据对用户 B 的读取、修改、删除均返回 403 或 404，且数据库没有变化。
4. 正常 CRUD、重复提交、边界长度、非法 ID、空结果和不存在资源。
5. 上传类型/大小、网络超时、SSH/SMTP/GitHub 失败等工具特有异常能转换为稳定错误码。
6. 数据分类、用量统计、按类别或时间清理，以及清理单用户时不影响其他用户。
7. Scheduler 回调幂等；一个用户失败不阻止其他用户；不会因 import 启动后台线程。

测试使用 `tmp_path` 覆盖 `storage_dir` 与 `platform_db_path`，不写真实 `storage/`。优先测试 service 的所有权和数据行为，再用 FastAPI client 验证端点契约。
