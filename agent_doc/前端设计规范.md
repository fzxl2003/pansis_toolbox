# 前端设计规范

## 目的与范围

本规范适用于 `tools/<tool_id>/frontend/` 中的所有 React 工具视图。目标是让工具具备一致的页面壳、可预测的 API 行为、清晰的加载/错误状态和可访问的交互，同时保留工具自身的专业工作流。

配套文档：[后端设计规范](./后端设计规范.md) · [环境配置指导](./环境配置指导.md)。文中的“必须/不得”是验收要求，“推荐/宜”允许在设计摘要中说明理由后调整。

## AI 设计协议

AI 在写 JSX 前必须先完成页面设计摘要，并与后端资源/API 对齐：

```text
主要用户与首要任务：
页面主标题、说明和唯一主操作：
概览指标（如需要）：
主内容结构：表格 / 卡片 / 分栏工作区 / 标签页
资源列表的空态、加载态和失败态：
主弹窗的核心字段：
二级弹窗及其摘要回显：
危险操作与确认方式：
窄屏重排方式：
需要持久化的 UI 偏好及位置：
```

实现顺序为：先搭信息层级和静态状态，再接 API，再补表单校验、错误与异步竞态，最后进行宽屏/窄屏视觉检查。不得把“接口能调用”视为页面完成。

## 框架接入与目录

每个工具在 `manifest.json` 的 `entry.frontend` 指向前端入口；入口必须默认导出 React 组件：

```tsx
export default function ToolView() {
  return <section className="tool-surface">...</section>;
}
```

目录建议如下：

```text
tools/<tool_id>/frontend/
├── index.tsx                # 工具页面入口；编排数据加载与主布局
├── components.tsx           # 可复用展示组件
├── types.ts                 # API DTO 与页面状态类型
├── utils.ts                 # 纯函数、格式化与 API 路径常量
└── style.css                # 仅工具特有样式
```

工具前端由 `scripts/generate_tool_views.py` 生成的 `frontend/src/registry/generatedToolViews.ts` 懒加载。不要手工编辑生成文件；新增、删除、启用工具后运行：

```bash
npm run check:tools
npm run generate:tools
```

框架会在工具页提供标准返回入口、加载占位、错误边界以及 `standard`、`fullscreen`、`flexible` 三种 `displayMode`。普通工具使用 `standard`；需要专注工作区的工具使用 `fullscreen`；确有两种视图需求才使用 `flexible`。

工具入口应显式 `import './style.css'`。当前项目虽安装 Tailwind，但现有工具主要使用带命名空间的普通 CSS；新工具默认沿用这一方式，不在工具内重置全局 token、`body`、按钮或表单标签。

首页 Lucide 工具图标当前只在 `ToolCard.tsx` 映射少量名称。选择未映射图标时会回退为 `Wrench`；若新工具需要新的 Lucide 图标，应同时在共享映射中显式注册并构建验证。也可以把图片放入工具 `assets/`，用 `{ "type": "image", "src": "...", "alt": "..." }` 声明。

根据目标形态选择参考工具，只借鉴结构和交互，不复制业务代码：

| --- | --- | --- |

如果现有实现与本规范冲突，以本规范为新工具标准；不要复制其历史存储路径、局部样式或权限缺口。

## 信息架构与视觉层级

1. 一个工具页面只解决一个明确的工作流。先展示当前状态和最常用操作，再放置筛选、历史、批量操作和高级设置。
2. 采用页面标题、简短说明、主操作和内容区域的结构；避免在工具内部重复实现平台侧栏、账户入口或全局设置入口。
3. 默认使用主框架已有的基础类与设计 token，例如 `page-stack`、`tool-surface`、`primary-button`、`secondary-button`、`empty-state`、`inline-link`。工具特有样式放入自身 `style.css` 并以工具前缀命名，例如 `.gb-`、`.csm-`。
4. 不使用全局标签选择器、`!important`、固定覆盖平台布局或不受约束的 `z-index`。全屏工具应交由 manifest 和 `ToolPage` 处理，不自行隐藏应用壳。
5. 有破坏性的操作使用明确的危险样式、操作对象和二次确认；不要只使用图标表达删除、停止、覆盖或发布。
6. 界面必须有明确层次：页面级信息用于概览和主操作，卡片/面板用于同一任务分组，行内控件只承载即时、简单编辑；不要把概览、配置、历史、权限和危险操作堆在同一个平面区域。
7. 表单字段较多时，主界面只展示核心字段和摘要。低频、高级、可重复或独立的子配置（如凭据、权限、变量、规则、通知、主题、模板）应从主编辑弹窗打开二级弹窗，而不是无限拉长主表单。

推荐页面骨架：

```text
页面标题 + 一句话说明                         [次操作] [主操作]
┌────────────┬────────────┬────────────┐
│ 关键指标/状态│ 关键指标/状态│ 关键指标/状态│   可选，没有真实价值时省略
└────────────┴────────────┴────────────┘
┌──────────────────────────────────────┐
│ 区块标题 + 解释                      [刷新/筛选]
├──────────────────────────────────────┤
│ 表格、卡片列表或主工作区                         │
└──────────────────────────────────────┘
```

页面中只保留一个视觉最强的主操作。筛选、刷新、导入和批量操作属于次操作；编辑、删除等资源操作放入对应行或详情上下文。

## 视觉风格

工具页应是清爽、信息密集但不拥挤的工作台风格，而不是复制其博客管理页面的具体组件。核心观感是：浅色低对比背景上的白色实体内容面、Slate 灰阶文字、单一靛蓝主色，以及依靠边框和留白形成层次。

### 色彩与层级

局部配色可作为工具局部 UI 的参考：

| 语义 | 推荐色彩 | 用法 |
| --- | --- | --- |
| 主文字 | `#1e293b` | 标题、主要数值、核心内容 |
| 次级文字 | `#64748b` | 说明、时间、辅助元信息 |
| 边框 | `#e2e8f0` | 卡片、表格分隔、分区边界 |
| 柔和背景 | `#f8fafc` | 行内信息块、次级区域、悬浮态 |
| 主操作 | `#4f46e5` | 创建、保存、确认等单一主路径 |
| 主操作悬浮 | `#4338ca` | 可点击的 hover 反馈 |
| 成功 | 深色 `#166534` / 浅底 `#dcfce7` | 成功状态与正向完成 |
| 失败/危险 | 深色 `#991b1b` / 浅底 `#fee2e2` | 错误、删除、不可逆操作 |
| 进行中 | 深色 `#1d4ed8` / 浅底 `#dbeafe` | 加载、同步、处理中 |
| 待处理 | 深色 `#92400e` / 浅底 `#fef3c7` | 等待、警告、需要关注 |

页面最多一个主色。状态色只表达状态，不能被用作普通装饰。优先使用浅色状态底加深色文本/图标，避免大面积高饱和色块；确保文字与背景保持足够对比度。

### 排版、间距与容器

- 使用平台的系统无衬线字体栈；正文默认 13–14 px，辅助文字 11–12 px，页面主标题约 25 px，区块标题约 16 px。
- 标题字重约 650，正文避免过粗；可用轻微负字距强调页面标题，但正文和表格不使用紧缩字距。
- 使用 4 px 的间距节奏：组件内部常用 6/8/12 px，卡片内边距 15–18 px，页面区块间距 16–22 px。
- 信息卡片使用白底、`#e2e8f0` 的 1 px 边框和 8–10 px 圆角；页面壳已提供玻璃化 surface 时，不再叠加重阴影。
- 模态框使用白色实体面、12 px 圆角、40–50 px 的柔和深色阴影；遮罩采用低透明深蓝灰，避免纯黑。

### 组件表现

- 主按钮高约 34 px、圆角 6 px；主按钮填充靛蓝，次按钮白底描边，幽灵按钮透明底。按钮内图标与文字间距约 7 px。
- 图标按钮保持约 30 × 30 px 的可点击面积，默认中性灰；悬浮时使用浅蓝底和蓝色图标，危险操作使用浅红底和红色图标。
- 状态使用圆角胶囊标签，文本约 12 px；标签同时显示文字与颜色，进行中状态可搭配旋转图标。
- 表格表头使用 11 px 大写或高辨识度标签、弱化灰色；行使用细分割线，悬浮仅给予近白蓝背景。长路径、仓库名和错误文本必须截断或限制行数，并保留完整内容的可访问方式。
- 空状态应居中、有低饱和图标、简短标题、解释与下一步操作；避免只显示“暂无数据”。
- 表单标签使用较小但清晰的深灰文字；输入框使用白底、浅灰边框，焦点时使用靛蓝边框与柔和的 3 px 外发光。
- 主编辑弹窗只负责资源的基础信息和提交动作；二级弹窗负责一个有独立标题、保存/取消动作的子任务。二级弹窗层级必须高于主弹窗，并使用更深一层遮罩，但同一时刻最多打开一层二级弹窗。
- 主弹窗中以摘要行、状态标签或“配置…”按钮呈现二级配置的结果；关闭二级弹窗后，立即回写摘要和校验结果，避免用户不知道修改是否生效。
- 若字段数量虽多但高度关联、必须一次性比较或共同校验，则使用分组、分步表单或可折叠区块；不要为了形式而把每个字段拆成弹窗。
- 弹窗层级建议主弹窗 `z-index: 1000`、二级弹窗 `z-index: 1010`；具体数值可调整，但必须统一集中定义，不能让各组件随意递增。
- 二级弹窗打开时主弹窗保持可见但不可交互。若二级内容只是主表单的一部分，点击“确认”只写回主表单草稿，最终由主弹窗统一保存；若二级内容是独立服务端资源，必须明确显示“已保存”，不能让用户误以为仍需提交主表单。

### 动效与响应式

- 仅对 hover、焦点、开关、加载和轻量展开使用 150–180 ms 的短动效；避免与任务完成无关的循环或大幅位移动画。
- 加载状态使用旋转图标或骨架，不用阻塞弹窗替代页面局部加载。
- 640 px 以下将双列表单、指标卡转换为单列；模态框边距缩至约 10 px；工具栏和页脚允许换行。
- 表格保持可横向滚动或改为卡片，不能为了适应窄屏隐藏关键状态、名称或操作。



## 状态与数据加载

每个异步区域都必须具备加载、空、成功和失败状态。初始加载应呈现可辨识骨架或“正在加载”；刷新失败不应清空已成功加载的数据，而应保留旧数据并显示可重试错误。

建议把 API DTO、表单状态与临时 UI 状态区分开：

```tsx
type ServerDto = { id: string; name: string; updatedAt: string };
type ServerForm = { name: string; host: string };
type LoadState = 'idle' | 'loading' | 'ready' | 'error';
```

涉及多次并发请求时，使用请求序号或当前资源 ID 守卫，避免旧响应覆盖新选择。当前共享 API client 尚未接收 `AbortSignal`；需要取消请求时先扩展共享 client，再使用 `AbortController`，不要为单个工具复制一套 JSON fetch。轮询仅在页面可见且资源已选中时执行，组件卸载时必须清理 timer、WebSocket、终端和其他订阅。项目启用了 React StrictMode，effect 在开发环境可能执行两次，初始化和清理逻辑必须可重复。

## API 客户端与错误处理

统一使用 `frontend/src/api/client.ts` 提供的接口：

```tsx
import { apiDelete, apiGet, apiPost, apiPostForm, apiPut, ApiError } from '../../../frontend/src/api/client';

const items = await apiGet<Item[]>('/api/tools/example/items');
const created = await apiPost<Item>('/api/tools/example/items', payload);
```

这些函数会自动使用 `credentials: 'include'` 携带平台认证 Cookie，并把统一错误响应转换为 `ApiError`。不要直接在工具中复制 `fetch` 包装、手工拼接认证 Cookie，或把 Token 存入浏览器。

- 对 `ApiError` 展示面向用户的错误消息；若 `code === 'LOGIN_REQUIRED'`，使用 `loginUrl` 引导登录。
- 不把后端原始响应、SQL、堆栈、Cookie 或凭据渲染到页面或 console。
- 上传使用 `apiPostForm`，不要自行指定 `Content-Type`，由浏览器设置 multipart boundary。
- API 路径集中于 `utils.ts` 或常量，使用 manifest 声明的前缀；不要把同一前缀散落在多个组件中。
- 文件流、SSE、WebSocket 或非 JSON 代理响应不适用当前 JSON client，可以使用对应浏览器 API，但仍须使用同源地址、平台 Cookie、统一错误语义和组件卸载清理。
- 若工具允许匿名打开但核心 API 需要登录，先用 `fetchMe()` 判断并复用 `frontend/src/components/LoginPanel`，不要自行制作登录表单或处理会话 Cookie。

框架前端还提供以下可复用模块：

| 模块 | 用途 |
| --- | --- |
| `frontend/src/api/client.ts` | `apiGet`、`apiPost`、`apiPut`、`apiDelete`、`apiPostForm`、`ApiError` |
| `frontend/src/api/auth.ts` | 当前登录用户、登录/退出与密码相关 API；工具通常只需 `fetchMe()` |
| `frontend/src/api/settings.ts` | SSH 服务器、GitHub Key、邮件与代理设置的共享 DTO/API |
| `frontend/src/api/tools.ts` | 工具状态、可见性和存储管理 DTO/API |
| `frontend/src/api/widgets.ts` | 小组件列表、数据和布局 API |

工具需要共享平台资源时优先导入这些 DTO/API；若必须调用同一平台端点但缺少封装，应先补充共享模块，而不是在工具内创建不同字段定义。

其中邮件配置和全局代理配置是管理员设置能力，普通工具不应直接展示或修改；工具后端只消费统一邮件发送与域名代理决策。SSH 服务器与 GitHub Key 的共享前端 API会按当前用户权限返回脱敏数据。

## 推荐前端骨架

```tsx
import { useEffect, useState } from 'react';
import { Loader2, Plus, RefreshCw } from 'lucide-react';

import { apiGet } from '../../../frontend/src/api/client';
import './style.css';

const API = '/api/tools/example-tool';

type Item = { id: string; name: string; updatedAt: string };

export default function ToolView() {
  const [items, setItems] = useState<Item[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState('');

  async function load() {
    setError('');
    try {
      const result = await apiGet<{ items: Item[] }>(`${API}/items`);
      setItems(result.items);
    } catch (exc) {
      setError(exc instanceof Error ? exc.message : '加载失败');
    } finally {
      setLoading(false);
    }
  }

  useEffect(() => { void load(); }, []);

  return (
    <section className="example-tool tool-surface">
      <header className="example-header">
        <div><h1>示例工具</h1><p>一句话说明当前页面能完成什么。</p></div>
        <button className="example-btn example-btn-primary" type="button"><Plus size={16}/>新建</button>
      </header>
      {error && <div className="example-alert error" role="alert">{error}</div>}
      <section className="example-panel">
        <header><div><h2>资源</h2><p>解释列表的范围和状态。</p></div><button type="button" onClick={() => void load()}><RefreshCw size={15}/>刷新</button></header>
        {loading ? <div className="example-loading"><Loader2 className="example-spin"/>正在加载</div>
          : items.length === 0 ? <div className="example-empty">暂无资源，创建第一项开始使用。</div>
          : <div>{/* 表格或卡片 */}</div>}
      </section>
    </section>
  );
}
```

骨架只规定页面层级，不是完整功能。实际实现必须补充请求竞态保护、可访问标签、表单、二级弹窗、危险操作确认和工具测试。

## 表单、交互与可访问性

1. 每个输入项都有可见 `label`；图标按钮必须有 `aria-label` 或可读标题。
2. 在提交期间禁用重复提交，保留输入内容，并在字段附近呈现可恢复的校验错误。
3. 模态框支持 Escape 关闭、关闭按钮、焦点管理与点击遮罩关闭（破坏性确认除外）；关闭后焦点回到触发按钮。
4. 不能只依赖颜色表达状态；同步成功、失败、警告和运行中应同时使用文本、图标或形状。
5. 表格在窄屏下应可横向滚动、折叠为卡片或提供摘要，不能简单裁切关键列。
6. 日期以用户本地时区展示，并同时在必要处保留可读的绝对时间；字节、耗时和状态使用统一格式化函数。
7. 键盘焦点必须始终可见；打开弹窗后焦点进入弹窗，关闭后回到触发控件。二级弹窗关闭后回到主弹窗中的“配置”按钮。
8. 破坏性确认必须写出资源名称和后果；输入名称确认只用于特别高风险操作，普通删除使用清晰的二次确认即可。

## 浏览器存储与 Cookie

页面状态默认保存在 React 内存。需要跨刷新但仅影响当前浏览器展示的低风险偏好，可以使用 Cookie，例如公开博客的目录展开状态；Cookie 应小型、使用尽可能小的 `Path`，且不参与授权。

不得使用 `localStorage`、`sessionStorage`、IndexedDB 或 Cache Storage 保存认证信息、敏感数据、跨设备同步状态或会影响业务结果的数据。用户配置、工作流状态、历史和服务器端可见的偏好必须由工具 API 保存到用户工具数据库。

## 性能与资源释放

- 大列表使用服务器分页、搜索或虚拟化；不要一次加载无限历史或全部日志。
- 图片使用尺寸限制与懒加载；预览和下载显示进度或明确的等待反馈。
- 页面离开时关闭 WebSocket、EventSource、终端会话引用、轮询和临时 URL object。
- 对高频输入使用防抖；对刷新按钮避免同时发起相同请求。
