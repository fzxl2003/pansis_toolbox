# 环境配置指导

## 目标

本文说明开发、测试与生产部署环境的最小配置，并规定工具数据根目录如何配置。所有环境都必须将持久化存储收敛到 `STORAGE_DIR/data` 与 `STORAGE_DIR/user_data`。

配套文档：[后端设计规范](./后端设计规范.md) · [前端设计规范](./前端设计规范.md)。环境指导描述当前仓库实际构建与部署方式；修改工具依赖、sidecar 或运行端口时应同步更新本文件。

## AI 开发工作流

AI 创建新工具时，应把本文件中的命令当作交付门槛：

```text
阅读三份规范和参考工具
    ↓
输出设计摘要与存储/API/页面清单
    ↓
create_tool.py 创建骨架
    ↓
实现后端 + 定向测试
    ↓
实现前端 + 宽窄屏检查
    ↓
生成注册表 + 工具检查 + 全量构建
    ↓
双用户隔离、错误态、数据清理和部署冒烟测试
```

不要在没有读取当前仓库实现的情况下猜测框架 API；文档与代码不一致时，以代码为当前事实，并同步修正文档或框架后再继续。

## 本地开发环境

推荐 Python 3.11+、Node.js 22+，并使用独立 Conda 环境：

```bash
conda create -n pansis_toolbox python=3.11 nodejs=22 -c conda-forge
conda activate pansis_toolbox
python -m pip install -e ".[dev]"
npm --prefix frontend ci
npm --prefix tools/git_blog ci
```

`npm run dev` 与 `npm run build` 当前会先构建 Git Blog 静态资源，因此本地需要安装 `tools/git_blog` 的 Node 依赖。其他工具只有在自己的目录存在 `package.json` 时才安装；有锁文件使用 `ci`，没有锁文件才使用 `install`：

```bash
npm --prefix tools/<tool_id> ci
# 没有 package-lock.json 时：npm --prefix tools/<tool_id> install
```

这类 `node_modules` 是开发/构建依赖，不得由线上请求动态安装；生产镜像应在构建阶段准备它们。

新工具在 manifest 中增加 Python `dependencies` 后，本地开发环境也要安装对应版本；manifest 供 Docker 构建扫描，不会自动修改当前 Conda 环境：

```bash
python -m pip install 'package-name>=1.2'
```

复制并编辑本地环境变量文件：

```bash
cp .env.example .env
```

建议的开发配置：

```dotenv
APP_ENV=development
FRONTEND_ORIGIN=http://localhost:5173
STORAGE_DIR=storage
PLATFORM_DB_PATH=storage/data/platform.db
WIDGET_LAYOUT_PATH=storage/data/widget_layout.json
SESSION_SECRET=replace-with-a-random-development-secret
DEFAULT_ADMIN_USERNAME=admin
DEFAULT_ADMIN_PASSWORD=replace-this-development-password
```

`PLATFORM_DB_PATH` 与 `WIDGET_LAYOUT_PATH` 必须位于 `STORAGE_DIR/data/`。不要将它们配置到项目根目录、工具源码目录或用户目录。

`SESSION_SECRET` 必须是稳定的长随机值。修改它会使已有会话失效，并可能导致 SMTP、SSH、GitHub Key 等由其派生密钥加密的数据无法解密；生产环境要通过密钥管理或受限环境变量持久保存，不得每次启动随机生成新值。



启动与验证：

```bash
npm run generate:tools
npm run dev

# 另一个终端中
npm run check:tools
python -m pytest backend/tests/test_app.py
```

默认开发地址为前端 `http://127.0.0.1:5173/`、后端 `http://127.0.0.1:8000/`。

创建新工具并验证注册：

```bash
python scripts/create_tool.py example_tool
npm run check:tools
npm run generate:tools
```

`create_tool.py` 只创建最小骨架，不会生成数据库 schema、授权、前端完整状态或测试；后续实现必须遵循后端与前端设计规范。

## 存储目录初始化与权限

应用进程必须对整个 `STORAGE_DIR` 有读写权限。初始化时至少创建：

```text
storage/
├── data/
│   └── tools/
└── user_data/
```

开发环境不需要预先创建每个用户或工具目录，框架会按需创建；但任何新路径都必须在 `STORAGE_DIR` 内解析，且不得接受未经清理的用户输入作为目录段。


## Docker 生产部署

项目内置 Compose 配置将命名卷挂载为 `/app/storage`。启动前必须为生产环境覆盖默认密钥和管理员密码：

```bash
SESSION_SECRET='use-a-long-random-secret' \
DEFAULT_ADMIN_USERNAME='admin' \
DEFAULT_ADMIN_PASSWORD='use-a-strong-password' \
HOST_PORT=8000 \
FRONTEND_ORIGIN='http://localhost:8000' \
docker compose -f docker/compose.yml up -d --build
```

容器内必须保持下面的变量一致：

```dotenv
STORAGE_DIR=/app/storage
PLATFORM_DB_PATH=/app/storage/data/platform.db
WIDGET_LAYOUT_PATH=/app/storage/data/widget_layout.json
TOOLS_DIR=/app/tools
FRONTEND_DIST_DIR=/app/frontend/dist
```

生产时不要使用默认值 `change-me-in-production` 或 `admin123`。部署后检查：

```bash
docker compose -f docker/compose.yml ps
curl -fsS http://127.0.0.1:8000/api/health
```

当前认证实现把登录 Cookie 的 `Secure` 固定为关闭。若生产环境通过公网或 HTTPS 提供服务，必须先修复平台认证 Cookie 配置并验证代理传递的协议，再将部署视为合格；新工具不得另建认证体系规避这一平台限制。

## 工具运行环境要求

- Python 依赖统一声明在根项目或工具 `manifest.json` 的 `dependencies` 中，并在镜像构建阶段安装。
- Node 依赖使用工具自己的 `package.json` 与锁文件，并在镜像构建阶段安装和构建。
- Git、SSH、Docker CLI 或 sidecar 等外部程序应在 Dockerfile 或运维镜像中安装；请求处理代码只能调用已存在的可执行文件。
- 任何需要写磁盘的 sidecar 都必须接收一个合规的工具数据目录，例如公共 sidecar 使用 `/app/storage/data/tools/<tool_id>/`，用户会话使用 `/app/storage/user_data/<user_id>/tools/<tool_id>/`。
- 不把缓存、日志、密码文件或下载依赖写入 `/tmp`、`/app/tools`、当前工作目录或浏览器本地存储。

manifest 中的 `dependencies` 会由 Dockerfile 扫描并安装，但 `permissions` 目前只是声明，不提供容器或进程级沙箱。增加系统二进制、端口、sidecar 或 Node 服务时，同时更新 Dockerfile、Compose、README 和本文件，并说明健康检查与数据目录。

## 测试环境与隔离

- 测试必须使用 `tmp_path` 或独立测试存储覆盖 `STORAGE_DIR` 和 `PLATFORM_DB_PATH`，不得污染仓库的真实 `storage/`。
- 至少准备管理员、用户 A、用户 B；覆盖未登录、工具不可见、跨用户访问和管理员操作。
- 外部 SMTP、SSH、GitHub、代理和网络请求优先使用 monkeypatch/fake，测试超时与失败映射，不依赖真实公网成功。
- 含 Scheduler 的工具直接调用回调进行确定性测试，不通过 `sleep` 等待定时器。
- 前端构建只能证明类型与打包成功；关键界面仍需进行浏览器宽窄屏和键盘流程检查。

## 新工具接入前检查

```bash
npm run check:tools
npm run generate:tools
npm run build
python -m pytest tools/<tool_id>/tests -q
python -m pytest backend/tests/test_app.py -q
git diff --check
```

在提交前，额外检查新工具是否出现了不合规的落盘路径：

```bash
rg -n 'storage_dir /|localStorage|sessionStorage|indexedDB|mkdtemp|NamedTemporaryFile|npm install|npm ci' tools/<tool_id> backend
```

检查结果中的持久化写入必须能归入 `storage/data/tools/<tool_id>/` 或 `storage/user_data/<user_id>/tools/<tool_id>/`。测试使用的 `tmp_path`、运行时内存状态和远程服务器文件可单独评估，但不得成为实际部署的数据落点。

最终还应进行一次运行时冒烟检查：

1. 登录用户能在首页看到并打开工具，禁用或无权用户看不到或收到统一拒绝。
2. 核心创建、读取、更新、删除流程与刷新页面后的状态一致。
3. 用户 A 的资源不会出现在用户 B 的列表、详情、更新、删除、后台任务或用量统计中。
4. 空数据、非法输入、外部服务失败、网络超时和重复提交都有稳定反馈。
5. 管理设置中的工具数据用量与清理能覆盖该工具，清理单用户不影响其他用户。
6. Docker 镜像启动后健康检查成功，工具依赖、静态资源、sidecar 和数据目录均可用。

只有命令检查和上述行为检查都通过，才算完成新工具接入。

```text
最终报告新增文件、设计决策、实际验证命令与仍存在的限制。
```
